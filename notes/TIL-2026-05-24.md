# TIL: CAP Theorem, PACELC & Week 1 Summary (2026-05-24)

## 1. Caching Review: Single-Flight vs Soft TTL
- **Single-Flight (Mutex)**: 데이터의 정확도(Freshness)가 중요할 때 사용. 캐시 미스 시 하나의 요청만 DB로 보내고 나머지는 대기시킴. (예: 결제, 대출 심사 등)
- **Soft TTL (Stale-while-revalidate)**: 응답 속도(Latency/Availability)가 중요할 때 사용. 논리적 만료 시간(Soft TTL)이 지나도 물리적 만료(Hard TTL) 전이라면 구버전 데이터를 즉시 반환하고, 백그라운드에서 비동기로 DB를 조회해 캐시를 갱신. (예: 피드, 트렌드, 조회수 등)

## 2. CAP Theorem의 엄밀한 이해
- **Consistency의 진정한 의미**: 단순히 "동일한 데이터"가 아니라 "가장 최신의 데이터" (Linearizability, Strong Consistency)를 의미함. 모든 읽기는 가장 최근의 쓰기 결과를 반영해야 함.
- **Availability의 실무적 판별법 (HTTP Status Codes 매핑)**:
    - `2xx (Success)`, `3xx (Redirect)`, `4xx (Client Error)`: 시스템이 요청을 명확히 인지하고 응답했으므로 **가용성(A) 만족**. (특히 400번대는 클라이언트 잘못이지 시스템 자체는 정상 가동 중임을 의미)
    - `5xx (Server Error)`, `Timeout`: 시스템이 응답 능력을 상실했거나, 일관성(C)을 지키기 위해 의도적으로 응답을 거부(포기)한 상태이므로 **가용성(A) 실패**.

## 3. PACELC 정리와 실무 적용
- 분산 시스템에서 네트워크 파티션(P) 상황 외에, 평상시(E)에도 **지연시간(L) vs 일관성(C)** 의 트레이드오프가 존재함.
- **결제 시스템의 예**: 장애 시 PA/ELC 중 **PC/EC** 선택. 즉, 평상시에도 지연시간(L)을 손해 보더라도 무조건 일관성(C)을 선택하여 데이터의 정확성을 보장해야 함.

## 4. Week 1: Core Concepts 총정리
1. **Latency**: 메모리 vs 디스크 = 10만 배 차이. 설계 결정(특히 캐싱/샤딩)은 예상 수치(QPS, 스토리지)로 정당화해야 함.
2. **Networking**: 기본은 REST. 실시간 양방향은 WebSocket, 단방향 스트리밍(서버->클라이언트)은 SSE.
3. **Data**: 일관성과 관계가 중요하면 B-Tree 기반 RDBMS, 무한한 스케일링과 쓰기 속도가 중요하면 LSM-Tree 기반 NoSQL.
4. **Caching**: Cache-Aside가 실무의 90%. 
5. **Scaling**: 단일 DB의 한계(통상 쓰기 10k+ TPS, 용량 50TB+)를 넘을 때 샤딩 고려. 노드 증설/감소 시 데이터 재배치를 최소화하는 Consistent Hashing.
6. **Theory**: 설계 면접의 80% 이상은 AP + Eventual Consistency(최종 일관성)를 기본으로 채택하며, 결제/재고 등 크리티컬한 도메인만 CP(Strong Consistency)를 채택.
