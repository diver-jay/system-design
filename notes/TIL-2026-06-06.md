# TIL: 마이크로서비스 아키텍처(MSA) 데이터 조회 패턴 종합

## 📅 학습 일시: 2026-06-06

---

### 1. 배경: MSA 환경에서의 데이터 조회 잔혹사
- **모놀리식 아키텍처**: 단일 데이터베이스를 사용하므로 복잡한 데이터도 RDBMS의 강력한 `JOIN`과 인덱스 최적화 기능을 통해 단 한 줄의 SQL로 안전하고 빠르게 조회 가능. ACID 트랜잭션으로 실시간 일관성(Strong Consistency) 보장.
- **마이크로서비스 아키텍처(MSA)**: **'서비스별 데이터베이스(Database per Service)'** 원칙에 따라 데이터가 격리됨. 물리적·네트워크적으로 DB가 완전히 분리되어 있어 DB 레벨의 `JOIN`이 원천적으로 불가능해짐.

---

### 2. API 조합(API Composition) 패턴과 두 가지 딜레마
여러 서비스에 흩어진 데이터를 애플리케이션 레벨(API 조합기)에서 호출하여 조립하는 방식. 단순 조회에는 유용하나, **여러 서비스의 데이터가 얽힌 복잡한 조건 검색(필터링/정렬)**을 마주할 때 가혹한 이지선다(딜레마)에 빠짐.

#### 💡 예시 시나리오: `findOrderHistory()` (마라탕 주문 내역 검색)
- **주문/주방 서비스**: 메뉴 데이터("마라탕")를 가지고 있어 키워드 필터링 가능.
- **배달/회계 서비스**: '주문 ID(Order ID)'는 가지고 있으나, 메뉴 정보가 없어 "마라탕" 조건으로 DB 레벨 필터링 불가.

#### ❌ 딜레마 1: 인-메모리 조인 (In-memory Join) -> 메모리 폭발
- **방식**: 배달/회계 서비스에서 특정 고객의 **모든 전체 데이터(M개)**를 네트워크로 무식하게 긁어온 뒤, API 조합기 메모리 안에서 짝을 맞춤.
- **자료구조적 최적화**: 애플리케이션 코드에서 해시맵(HashMap)을 활용하면 CPU 연산 시간 복잡도를 `O(N * M)`에서 `O(N + M)`으로 획기적으로 줄일 수 있음.
- **한계**: CPU 연산은 최적화할 수 있어도, 데이터 전송량(Payload) 자체를 줄일 수 없음. 기가바이트 단위의 거대한 데이터를 RAM에 올려야 하므로 **서버 메모리(Heap) 폭발(OOM)** 및 가비지 컬렉션(GC) 병목으로 서버가 다운될 위험이 큼.

#### ❌ 딜레마 2: ID 기반 순차/대량 조회 -> 네트워크 폭발
- **방식**: 주문/주방 DB에서 '마라탕'에 해당하는 주문 ID(예: 1번, 5번 영수증)를 먼저 찾아낸 뒤, 해당 ID들만 들고 배달/회계 서비스에 필요한 정보만 핀셋 쿼리.
- **한계**: 가져오는 데이터양은 최소화되지만, 조건에 맞는 데이터가 많을수록 다른 서비스를 호출하는 **과도한 네트워크 트래픽(N+1 쿼리 문제)**이 유발되어 통신 효율이 극도로 저하됨.

#### 🚨 절대적인 장벽: 네트워크 지연(Network Latency)
API 조합 패턴이 '반쪽짜리 솔루션'이 될 수밖에 없는 가장 결정적인 이유는 **네트워크 지연**이라는 물리적 한계 때문임.
- DB 내부 조인은 동일 서버 내 메모리 버스 통신이므로 **나노초(ns) / 마이크로초(µs)** 단위로 끝남.
- 반면 API 조합기의 외부 호출은 랜선과 프로토콜을 거치는 물리적 통신이므로 **밀리초(ms)** 단위가 소요됨.
- 1번 왕복에 10ms가 걸리는 API를 100번 호출하면(N+1 문제), 코드가 아무리 기가 막혀도 순수 네트워크 대기 시간만 **1초**가 소요되어 성능에 치명적인 결함이 발생함.

### 3. 단일 서비스 내에서의 조회 난관
여러 서비스를 엮는(JOIN) 문제가 전혀 아님에도, **"각 서비스의 목적에 맞춰 선택한 DB의 태생적 한계"** 때문에 단일 서비스 내부에서도 조회가 지옥처럼 어려워지는 상황이 발생함.

#### 📌 이유 1: 데이터를 가진 서비스에 쿼리를 구현하는 것이 부적절한 경우 (OLTP vs OLAP의 충돌)
> 데이터는 내가 가진 게 맞지만, 그 쿼리를 내 운영 DB에서 돌리면 본업(메인 비즈니스 트랜잭션)이 망가지는 경우.
- **결제 서비스의 '5년 치 회계 감사 리포트'**: 초당 수천 건의 카드 결제를 처리해야 하는 서비스에 수억 건의 테이블 풀스캔 통계 쿼리를 던지면 DB가 락(Lock)이 걸려 실제 고객들의 실시간 결제가 실패함.
- **리뷰 서비스의 '어뷰징 탐지 알고리즘'**: 실시간으로 가볍게 리뷰를 쓰고 읽는 환경에서, 머신러닝에 가까운 무거운 패턴 분석 집계 쿼리를 동시에 돌리는 것은 아키텍처 목적에 부적절함.

#### 📌 이유 2: 서비스 DB가 효율적인 쿼리를 지원하지 않는 경우 (기술적 한계)
> 서비스 성격에 맞춰 특정 DB를 선택했는데, 새롭게 필요한 기능이 그 DB 엔진의 태생적 한계를 벗어나는 경우.
- **지리 공간(Geospatial) 검색의 한계**: '음식점 서비스'가 대용량 확장성을 위해 DynamoDB(NoSQL)를 채택했는데, "내 주변 반경 3km 내 음식점 검색"이라는 좌표 계산 쿼리 능력을 DB가 자체 지원하지 않는 경우.
- **시계열 데이터 집계의 한계**: MySQL(RDBMS)로 배달원 위치를 관리하는데, "전체 배달원의 최근 24시간 동안 5분 단위 이동 속도 평균값" 같은 대량의 시계열 통계를 내야 해서 성능이 최악으로 떨어지는 경우.
- **관계망(Graph) 검색의 한계**: Redis(Key-Value)를 쓰는데 "내 친구의 친구들이 단골로 등록한 마라탕 가게 추천" 같은 거미줄처럼 얽힌 소셜 그래프 JOIN 연산이 불가능한 경우.

### 4. 조직적 관점: 관심사의 분리 (Separation of Concerns)
- **데이터 소유권(원본 관리) vs 쿼리 책임(무거운 검색)**은 별개의 문제임.
- **음식점 서비스 개발 팀의 본업**: 음식점 사장님들이 가게 정보를 등록하고 메뉴 가격을 수정(데이터 무결성 관리)할 수 있도록 돕는 것임.
- 만약 이 팀이 소비자들이 수시로 호출하는 대용량 검색 기능(`findAvailableRestaurants`)까지 떠안게 된다면, 검색 쿼리 배포 하나 때문에 정작 사장님들이 메뉴 수정을 못 하게 될까 봐 **늘 불안감에 시달리고 본업에 집중하지 못하게 됨.**
- 따라서 "재료(원본 데이터)는 음식점 서비스가 주되, 요리(무거운 검색 조회)는 조회 전담 서비스나 다른 팀이 가져가서 처리한다"는 **책임 분리**가 필수적임.

### 5. 구원투수: CQRS (Command Query Responsibility Segregation) 패턴
> *"어차피 분산 환경에서 실시간으로 네트워크를 넘나들며 데이터를 조립하거나 무리한 쿼리를 던지는 것은 물리적으로 불가능하다. 데이터를 변경하는 통로와 조회하는 통로를 완전히 찢어버리자!"*

#### 🔄 전통적 방식(비CQRS) vs CQRS 아키텍처
- **비CQRS (기존 상식)**: 하나의 도메인 모델(JPA의 ` @Entity` 등)과 하나의 운영 DB를 공유하여 C, R, U, D를 모두 처리함. 저장할 때의 데이터 모양과 조회할 때의 데이터 모양이 똑같음.
- **CQRS (새로운 패러다임)**: 영속적 데이터 모델과 모듈을 **명령(Command)**과 **조회(Query)** 두 편으로 완전히 갈라버림.

```
[ 비CQRS 방식 ]
REST API (CRUD) ──> 단일 도메인 모델 (Entity) ──> 단일 DB (CRUD 통합)

[ CQRS 방식 ]
HTTP POST/PUT/DELETE ──> 커맨드 모델 ──> 쓰기 DB (CUD 전담)
                                           │
                                    (도메인 이벤트 발행)
                                           ▼
HTTP GET ──────────────> 쿼리 모델 ───> 읽기 뷰 DB (R 전담 / 미리 JOIN 완료)
```

- **명령(Command) 측**: 생성/수정/삭제(CUD) 작업을 전담하며 복잡한 비즈니스 규칙을 안전하게 처리함. 상태가 변경되면 **'도메인 이벤트(Event)'**를 발행함.
- **조회(Query) 측**: 오직 조회(Read)만 전담함. 비즈니스 로직이 없어 구조가 단순하며, 오직 **쿼리 성능 및 목적에 최적화된 읽기 전용 뷰(View) DB**(예: Elasticsearch, 시계열 DB 등)를 독립적으로 유지함. 이벤트 핸들러가 백그라운드에서 이벤트를 구독하여 데이터를 동기화함.

#### 🤝 일관성과의 결단력 있는 타협: 최종 일관성 (Eventual Consistency)
- CQRS는 모놀리식 환경과 같은 완벽한 실시간 일관성(Strong Consistency)을 보장하지 못하며, 데이터 동기화 과정에서 미세한 시차(Replication Lag)가 발생함.
- 하지만 **"어차피 MSA 분산 환경에서 완벽한 실시간 일관성은 불가능하니, 논리적 모순이 없는 읽기 뷰 DB를 구축하여 압도적인 조회 퍼포먼스, 가용성, 그리고 팀 간의 관심사 분리를 쟁취하자"**라는 철학적 타협이자 패러다임의 전환임.
