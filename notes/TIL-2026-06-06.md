# TIL: MSA 데이터 조회 패턴 (API 조합의 한계와 CQRS의 필요성)

## 📅 학습 일시: 2026-06-06

---

### 1. 배경: MSA 환경에서의 데이터 조회 잔혹사
- **모놀리식 아키텍처**: 단일 데이터베이스를 사용하여 복잡한 데이터도 RDBMS의 강력한 `JOIN`과 인덱스 최적화 기능을 통해 단 한 줄의 SQL로 안전하고 빠르게 조회 가능.
- **마이크로서비스 아키텍처(MSA)**: **'서비스별 데이터베이스(Database per Service)'** 원칙에 따라 데이터가 격리됨. 물리적·네트워크적으로 DB가 분리되어 DB 레벨의 `JOIN`이 원천적으로 불가능해짐.

---

### 2. API 조합(API Composition) 패턴과 두 가지 딜레마
여러 서비스에 흩어진 데이터를 애플리케이션 레벨에서 조립하는 방식. 단순 조회에는 유용하나, **다중 서비스가 얽힌 복잡한 조건 검색(필터링/정렬)**을 마주할 때 가혹한 이지선다(딜레마)에 빠짐.

#### 예시 시나리오: `findOrderHistory()` (마라탕 주문 내역 검색)
- **주문/주방 서비스**: 메뉴 데이터("마라탕")를 가지고 있어 필터링 가능.
- **배달/회계 서비스**: '주문 ID'는 외래키 형태로 가지고 있으나, 메뉴 정보가 없어 "마라탕" 조건으로 DB 레벨 필터링 불가.

#### ❌ 해결책 1: 인-메모리 조인 (In-memory Join)
- **방식**: 배달/회계 서비스에서 특정 고객의 **모든 전체 데이터(M개)**를 네트워크로 무식하게 긁어온 뒤, API 조합기 메모리 안에서 짝을 맞춤.
- **자료구조적 최적화**: 애플리케이션 코드에서 해시맵(HashMap)을 활용하면 CPU 연산 시간 복잡도를 `O(N * M)`에서 `O(N + M)`으로 줄일 수 있음.
- **한계 (메모리 폭발)**: CPU 연산은 최적화할 수 있어도, 기가바이트 단위의 거대한 데이터 페이로드를 RAM에 올려야 하므로 **서버 메모리(Heap) 폭발(OOM)** 및 가비지 컬렉션(GC) 병목으로 서버가 다운될 위험이 큼.

#### ❌ 해결책 2: ID 기반 순차/대량 조회 (N+1 문제)
- **방식**: 주문/주방 DB에서 '마라탕'에 해당하는 주문 ID(예: 1번, 5번)를 먼저 찾아낸 뒤, 해당 ID들만 들고 배달/회계 서비스에 필요한 정보만 핀셋 쿼리.
- **한계 (네트워크 폭발)**: 가져오는 데이터양은 최소화되지만, 조건에 맞는 데이터가 많을수록 다른 서비스를 호출하는 **과도한 네트워크 트래픽(N+1 쿼리 문제)**이 유발되어 통신 효율이 극도로 저하됨.

### 3. 절대적인 장벽: 네트워크 지연(Network Latency)
API 조합 패턴이 '반쪽짜리 솔루션'이 될 수밖에 없는 가장 결정적인 이유는 **네트워크 지연**이라는 물리적 한계 때문임.

| 비교 대상 | 통신 속도 단위 | 특징 |
| :--- | :--- | :--- |
| **RDBMS 내부 JOIN** | 나노초(ns) / 마이크로초(µs) | 동일 서버 내 메모리 버스 통신, 최적화 엔진 탑재 |
| **API 조합기 외부 호출** | 밀리초(ms) | 랜선, 라우터, HTTP/gRPC 프로토콜을 거치는 물리적 통신 |

- 코드를 아무리 기가 막히게 짜고 서버 사양을 업그레이드(Scale-up)해도, **서버 밖을 나갔다 들어오는 물리적인 통신 시간 자체를 0으로 만들 수는 없음.**
- 1번 왕복에 10ms가 걸리는 API를 100번 호출하면 순수 네트워크 대기 시간만 **1초**가 소요되어 사용자 경험에 치명적인 결함을 장착하게 됨.

### 4. 구원투수: CQRS(Command Query Responsibility Segregation) 패턴
> *"어차피 실시간으로 네트워크를 넘나들며 데이터를 조립하는 것은 물리적으로 불가능하다. 조회를 할 때는 네트워크를 타지 않도록, 하나의 DB에 데이터를 미리 다 모아두자!"*

- **핵심 개념**: 상태를 변경하는 **명령(Command, 쓰기)**과 상태를 조회하는 **쿼리(Query, 읽기)**의 책임과 통로를 물리적으로 완전히 분리.
- **동작 원리**: 쓰기 전용 DB에 데이터가 변경되면, 시스템은 **이벤트(Event)**를 발행함. 이 이벤트를 구독하여 조회 성능에 최적화된 별도의 **'읽기 전용 뷰(View) DB'**에 데이터를 미리 조인하고 가공해서 채워둠.
- **일관성과의 타협**: CQRS는 완벽한 실시간 일관성(Strict Consistency)을 제공하지 못함. 데이터 동기화 과정에서 미세한 시차가 발생하는 **최종 일관성(Eventual Consistency)**을 수용하는 대신, **압도적인 조회 퍼포먼스, 복잡한 다중 서비스 쿼리 해결, 그리고 시스템 가용성 극대화**를 쟁취하는 패러다임 전환임.
