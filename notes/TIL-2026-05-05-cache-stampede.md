# TIL: Cache Stampede vs. Hot Key Cold Start (2026-05-05)

## 1. 개요
시스템 설계 면접에서 혼동하기 쉬운 두 가지 대규모 트래픽 부하 현상을 정리한다. 두 현상 모두 DB 과부하를 초래하지만, 발생 원인과 해결책이 다르다.

## 2. 비교 분석

| 구분 | 연예인의 신규 피드 (Hot Key Cold Start) | Cache Stampede (Thundering Herd) |
| :--- | :--- | :--- |
| **발생 원인** | 새로운 데이터가 생성되어 캐시가 비어있는 상태에서 트래픽 폭주 | 기존에 캐싱되어 있던 인기 데이터가 **TTL 만료**로 갑자기 사라짐 |
| **상황** | 데이터가 **처음** 생겼을 때 | 잘 있던 데이터가 **순간적으로** 증발했을 때 |
| **중복성** | 한 번은 DB에서 읽어와야 하는 필수적 부하 | 이미 캐시에 있던 것이므로 **중복된 비효율적 쿼리** (불필요한 부하) |
| **해결 핵심** | **Pre-caching**: Write 시점에 캐시에 먼저 밀어넣기 (Push) | **Locking**: "한 명만 DB 가서 갱신해!"라고 제어 (Pull 제어) |

## 3. 핵심 통찰
- **Cold Start**는 데이터의 **생성** 시점에 발생하며, 서비스 로직(Write) 단계에서 캐시를 미리 채워줌으로써 방어할 수 있다.
- **Cache Stampede**는 캐시 시스템의 **관리(만료)** 단계에서 발생하며, 동일한 쿼리가 수만 번 중복 실행되지 않도록 Mutex Lock이나 확률적 조기 만료(Probabilistic Early Expiration)를 사용한다.
