# [Review & TIL] MSA Database per Service 3대 목적 & API Composition의 2가지 딜레마 (2026-10-20)

## 1. 왜 MSA는 `Database per Service`를 강제하는가?
> 원본 노트: [`notes/TIL-2026-06-06.md`](./TIL-2026-06-06.md), [`notes/TIL-2026-06-04.md`](./TIL-2026-06-04.md)

단순히 서버 가용성(Availability) 때문이 아니라, 다음 **3가지 핵심 이유** 때문에 서비스마다 DB를 물리적·논리적으로 분리한다:

1. **배포 독립성 (Independent Deployability)**
   - 다른 서비스 팀과 배포 일정을 조율하지 않고도 각 팀이 독자적으로 서비스를 개발·배포하기 위함.
2. **스키마 디커플링 (Schema Decoupling / 데이터 캡슐화)**
   - DB 스키마를 서비스 내부의 비공개 구현 세부사항(Private Implementation Detail)으로 숨겨, 특정 서비스의 컬럼/테이블 변경이 다른 서비스 코드로 번지는 **변경 파급 효과(Design-time Coupling)** 를 원천 차단하기 위함.
3. **장애 전파 사전 차단 (Fault & Resource Isolation)**
   - 한 서비스의 무거운 쿼리, 테이블 Lock, CPU/커넥션 고갈이 다른 서비스의 핵심 트랜잭션으로 전파되는 **런타임 간섭(Runtime Coupling / Noisy Neighbor)** 을 물리적으로 격리하기 위함.
   - *(+ 부가 이점: 서비스 특성에 맞는 DB를 각각 선택하는 **폴리글랏 퍼시스턴스, Polyglot Persistence**)*

## 2. API 조합(API Composition) 패턴과 2가지 딜레마
- **배경**: `Database per Service`로 인해 DB 레벨의 **`JOIN`** 이 불가능해지면서, 애플리케이션 레벨(API 조합기)에서 여러 서비스를 호출해 데이터를 조립해야 함.
- **문제 상황**: `'마라탕'(주문 서비스 DB)` 이면서 `'배달 완료'(배달 서비스 DB)` 인 주문 내역처럼 여러 서비스에 걸친 조건 검색 시 두 가지 딜레마에 빠짐:

| 구분 | 방식 1: 인-메모리 조인 (In-memory Join) | 방식 2: ID 기반 순차/대량 조회 |
|---|---|---|
| **동작 방식** | 각 서비스에서 조건 데이터를 **한 번에 통째로 다 긁어와서** API 조합기 메모리(RAM)에서 조립 | 1차로 `주문 서비스`에서 '마라탕' `order_id` 목록만 뽑은 뒤, 2차로 `배달 서비스`에 ID별로 조회 |
| **핵심 트레이드오프** | 호출 횟수를 줄이는 대신 **메모리와 네트워크 Payload를 혹사** | 메모리를 아끼는 대신 **응답 속도(네트워크 왕복 Latency)를 희생** |
| **치명적 한계 (병목)** | `HashMap`으로 CPU 연산은 $O(N+M)$ 최적화가 가능하나, 대량 데이터 전송 및 **서버 Heap 메모리 폭발(`OOM`) / `GC 멈춤`** 발생 | 병렬 호출 불가(직렬화) + 조건 데이터가 많을수록 **과도한 네트워크 왕복(`N+1 쿼리 문제`)** 으로 Latency 폭발 (DB 내부 `100ns` vs 네트워크 `ms` 단위) |

## 3. 클린 아키텍처 심화 Q&A: 경계의 물리적 3단계 & 네트워크 분리의 오해
> 연관 노트: [`notes/TIL-2026-07-08.md`](./TIL-2026-07-08.md) (클린 아키텍처 17장·18장·27장)

### 3.1 "경계선을 긋는다(나눈다)" = 무조건 서비스를 쪼갠다는 뜻인가? (No!)
- **원칙**: *"변경의 이유와 시점이 같은 것은 묶고(응집도 $\uparrow$), 다른 것은 나눈다(결합도 $\downarrow$)."*
- 이때 '나눈다'는 것은 물리적 형태에 따라 **3단계(Decoupling Modes)** 로 진화하며, **단일 서비스 내 로직 분리(1단계)가 모든 것의 기본**이다:
  1. **소스 수준 분리 (Source-Level — 모놀리식 내 패키지/인터페이스 분리)**: 한 프로젝트·한 프로세스 안에서 폴더(패키지)와 인터페이스(DIP)로 분리. 메모리 내 함수 호출(`ns` 단위).
  2. **배포 수준 분리 (Deployment-Level — 멀티 모듈 / `.jar`, `.dll` 분리)**: 여전히 **한 서버 프로세스(같은 메모리)** 에 올라와 일반 함수 호출로 동작하지만, 빌드 파일(`.jar`)을 분리함.
     - **1단계 $\rightarrow$ 2단계 전환 정당성**:
       - ① **변경 주기 차이**: 자주 바뀌는 어댑터 모듈 때문에 안정적인 코어 모듈까지 매번 전체 재빌드/재테스트하는 비용 절감.
       - ② **경계 침범의 물리적(컴파일 타임) 차단**: 같은 프로젝트 폴더만 나누면 실수로 코어 로직에서 DB 클래스를 `import` 해도 통과되지만, `.jar` 빌드 단위를 분리하면 `domain.jar`에서 `db.jar`를 참조하는 순간 **컴파일 에러**로 강제 차단됨.
  3. **서비스 수준 분리 (Service-Level — MSA 분리)**: 별도 프로세스/서버로 쪼개고 네트워크(`ms` 단위)로 통신. 리소스/장애 격리 및 독립 스케일링이 필요할 때만 선택.

### 3.2 독립된 2개 서비스로 나누고 네트워크로 통신하면 의존성(Dependency)이 사라지는가? (No!)
- **결합 분리의 오류 (The Decoupling Fallacy — 클린 아키텍처 27장)**:
  - 소스코드를 2개의 마이크로서비스로 쪼개고 네트워크(HTTP/gRPC)로 통신한다고 해서 의존성이 사라지는 것이 절대 아니다.
  - 메모리 `import` 결합이 **① 데이터(JSON API 스키마) 의존성**과 **② 런타임(시간적) 의존성**으로 **형태만 바뀐 것**이다 (상대 서비스가 JSON 필드를 바꾸면 내 코드도 깨지고, 상대 서버가 죽으면 내 요청도 실패함).
- **진짜 의존성 역전(DIP)의 의미**:
  - 의존성이 증발하는 것이 아니라 **"누가 누구에게 맞춰주느냐(방향)"** 를 통제하는 것.
  - 내 핵심 비즈니스 로직 안에 외부 서비스 URL이나 전용 JSON 포맷을 직접 박지 않고, **바깥쪽 어댑터(`Adapter`)가 네트워크 통신/변환을 대신 흡수**하게 하거나 **비동기 이벤트(Kafka 등)** 를 발행하여 외부 변경으로부터 핵심 로직을 보호하는 것이 본질이다.
