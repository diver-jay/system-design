# TIL: 2026-06-04 (MSA 데이터 조회 패턴)

## 📖 학습 내용: 마이크로서비스 아키텍처(MSA) 데이터 조회 패턴
> 크리스 리처드슨 저 『마이크로서비스 패턴』 단원 7.1 ~ 7.2 요약

### 1. 배경: 왜 새로운 조회 패턴이 필요한가?
- **과거 (모놀리식)**: 단일 DB 사용. 복잡한 데이터도 SQL `JOIN`으로 한 번에 조회 가능. ACID 트랜잭션으로 일관성 보장.
- **현재 (MSA)**: **서비스별 데이터베이스(Database per service)** 원칙. 데이터가 각 서비스 DB에 격리되어 있어 DB 레벨의 `JOIN`이 불가능함.
- **해결책**: 애플리케이션 레벨에서 데이터를 조립하는 **API 조합(Composition) 패턴**과 **CQRS 패턴**이 필요.

### 2. API 조합(API Composition) 패턴
- **구조**:
  - **API 조합기(Composer)**: 클라이언트의 요청을 받아 여러 서비스(Provider)에 쿼리하고 결과를 조립.
  - **데이터 프로바이더(Provider)**: 각자의 DB를 가진 개별 마이크로서비스.
- **조합기 위치 옵션**:
  1. **서비스 클라이언트**: 프론트엔드에서 직접 호출. 단순하지만 네트워크 지연 및 기기 부하 증가.
  2. **API 게이트웨이**: 외부 네트워크 효율 최적화. 하지만 게이트웨이 로직 비대화 위험.
  3. **BFF (Backend for Frontend)**: 플랫폼별 맞춤 가공 가능. 관리 포인트 및 인프라 비용 증가.

### 3. 설계 이슈 및 최적화
- **병렬 호출**: 순차적 호출은 지연 시간의 합이 되므로 성능 저하. 의존성이 없는 경우 반드시 **동시(Parallel) 병렬 호출** 수행.
- **리액티브 프로그래밍**: `CompletableFuture`, `RxJava` 등을 활용하여 Non-blocking으로 효율적 구현.

### 4. 단점과 한계
- **가용성 저하**: 여러 서비스가 모두 정상이어야 기능함. (가용성 = 각 서비스 가용성의 곱)
  - *대응*: 캐시 활용(과거 데이터라도 반환), 부분 응답(Graceful Degradation).
- **데이터 일관성 결여**: 분산 DB 환경에서 글로벌 트랜잭션이 없으므로 시차에 의한 불일치 발생 가능.
  - *대응*: 비즈니스적 타협(최종 일관성 수용) 또는 **CQRS 패턴**으로 전환.

### 5. CQRS (Command Query Responsibility Segregation)
- **도입 배경**: API 조합 패턴으로 해결하기 어려운 복잡한 쿼리나 엄격한 일관성/성능 요구 시 사용.
- **핵심**: 상태 변경(Command)과 조회(Query) 통로를 분리.
- **조회 전용 뷰 DB**: 실시간으로 동기화되는 별도의 조회 전용 DB를 구축하여 성능과 일관성을 확보.
