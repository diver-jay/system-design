# [Review & TIL] 아키텍처 분리 3대 Hell 진단 & 분산 쓰기 지옥에서 HTTP vs Kafka (2026-10-23)

> 마스터 레퍼런스: [`notes/references/decision-framework.md`](./references/decision-framework.md)

## 1. 아키텍처 경계를 잘못 나눴을 때 발생하는 3대 Hell (실무 페인 포인트)
- **① 시간축을 잘못 나눴을 때 (`분산 모놀리식` 지옥)**
  - 변경 이유와 주기가 같은 도메인을 쪼개놓아, 기능 하나 수정에 **여러 Repo PR + 배포 순서 수동 조율 의존성**이 생김.
  - 신/구버전 공존을 위한 **하위 호환성 유지 비용**이 들고, 결국 **가장 느린 개발/배포 주기에 전체 생산성이 하향 평준화**됨.
- **② 공간축(DB/스키마)을 잘못 나눴을 때 (`JOIN 실종` & `분산 트랜잭션` 지옥)**
  - **조회 지옥 (`JOIN` 불가 $\rightarrow$ `API Composition` 딜레마)**:
    - 통째로 퍼와서 메모리 조인(`In-memory Join`) $\rightarrow$ **서버 메모리(`OOM`) 및 `GC 멈춤` 폭발**
    - ID만 뽑아서 건건이 조회(`ID 기반 순차 조회`) $\rightarrow$ **`N+1` 네트워크 왕복으로 응답 속도(Latency) 폭발**
  - **쓰기 지옥 (`ACID` 불가)**:
    - RDBMS의 공짜 `ROLLBACK`을 잃어버려 **보상 트랜잭션(`Saga`)** 과 일시적 데이터 불일치(`Eventual Consistency`)를 직접 감당해야 함.
- **③ 자원/런타임축을 잘못 나눴을 때 (`네트워크 홉 낭비` & `SPOF 확산` 지옥)**
  - 물리적 격리나 보안 목적 없이 단순 1:1 패스스루 서버를 분리해 **5,000배 Latency 세금(`100ns` $\rightarrow$ `0.5ms`) 누적** 및 중간 장애점(`SPOF`) 증가.

## 2. 공간축 '쓰기 지옥' 해결책 & `HTTP` vs `Kafka`의 본질 비교

### 2.1 쓰기 지옥 해결의 우선순위
1. **1순위 (경계 재조정 — 다시 합치기)**: 원래 한 몸(같은 Aggregate)이어야 할 도메인을 과도하게 쪼개서 생긴 고통이라면, **다시 하나의 서비스/DB로 합쳐 로컬 `ACID` 트랜잭션으로 해결**하는 것이 가장 싸고 확실한 정답이다.
2. **2순위 (물리적으로 합칠 수 없을 때)**: 팀이나 트래픽 격리 때문에 어쩔 수 없이 DB가 나뉘어 있다면, **동기 `HTTP`를 쓰든 비동기 `Kafka`를 쓰든 진짜 `ACID`는 불가능하며 둘 다 `Eventual Consistency(최종 일관성)`** 이다.

### 2.2 왜 `HTTP req/resp`로 호출해도 `ACID`가 깨지는가?
- **부분 실패(Partial Failure)**: `B 서버(결제 DB)`는 `COMMIT` 후 `200 OK`를 보냈는데 **응답길에 네트워크 타임아웃**이 나거나, `A 서버(주문 DB)`가 응답을 받고 **`COMMIT` 직전에 OOM/DB 순단으로 죽으면** 결제만 되고 주문은 롤백되는 데이터 불일치가 터진다.
- **DB 커넥션 고갈**: DB A의 `@Transactional`을 열어둔 채 느린 HTTP 응답을 기다리면 DB 커넥션 풀이 순식간에 고갈된다.
- **공통 필수 세금 4종**: 따라서 `HTTP`든 `Kafka`든 정합성을 맞추려면 똑같이 **① 중간 상태(`PENDING`) 선 커밋**, **② 멱등성(`Idempotency-Key`)**, **③ 보상 로직(`Saga`)**, **④ 중간 유실 복구 메커니즘**을 구현해야 한다.

### 2.3 그렇다면 `HTTP` vs `Kafka`는 무엇이 다른가?
정합성 수준이 아니라 **"유저 UX(응답 타이밍)"** 와 **"중간 유실 복구(재시도)를 누가 대신 해주느냐"** 의 차이이며, 비즈니스 특성에 따라 선택(또는 혼용)한다.

| 구분 | 동기 `HTTP req/resp` | 비동기 `Kafka 이벤트` |
|---|---|---|
| **선택 기준 (도메인 특성)** | **즉시 거절(Validation/차감)** 이 필요한 핵심 경로 (카드 승인, 재고/좌석 선점, 쿠폰 사용) | 상대가 잠깐 죽어도 **내 핵심 요청(주문)은 무조건 성공**시키고 나중에 처리되면 되는 파생 작업 (알림 발송, 포인트 적립, 물류 전달, `CQRS` 동기화) |
| **유저 UX** | 요청 한 번에 **"완료/실패" 즉시 응답 가능** | 즉시 완료 응답 불가 ("접수됨" 응답 후 비동기 알림 필요) |
| **상대 서버(B) 장애 시** | B가 죽으면 **A도 즉시 실패** (런타임 강한 결합) | B가 죽어 있어도 **A는 성공**, B 복구 후 처리 (가용성 격리) |
| **중간 유실 복구 주체** | 개발자가 직접 **`PENDING` 상태 조회 배치(스케줄러/대사 작업)** 를 짜서 재시도/보상해야 함 | **`Transactional Outbox`** 로 발행만 보장하면 **Kafka 브로커가 보관 및 재전달**을 대신 해줌 |

## 3. AWS MSK(Managed Kafka)를 쓰면 자동으로 "무조건 처리"가 보장되는가? (No!)
단순히 코드에서 `db.save()` 뒤에 `kafka.send()`만 호출하면 여전히 메시지가 유실된다. 개발자가 직접 **3대 구멍(발행·보관·소비)** 을 막아야 `At-least-once(최소 1회 이상 처리)`가 보장된다:

1. **[발행 구멍 — `Dual Write` 방지]**: 내 DB `COMMIT` 직후 `kafka.send()` 직전에 서버가 죽어 메시지가 증발하는 것을 막기 위해, 같은 DB 트랜잭션 안에서 `outbox` 테이블에 메시지를 함께 `INSERT`하는 **`Transactional Outbox` 패턴**(+ Poller/CDC) 필수.
2. **[브로커 구멍 — 복제 내구성]**: 리더 브로커가 받자마자 죽어도 유실되지 않도록 Producer **`acks=all`** 설정 필수.
3. **[소비 구멍 — 유실 및 독성 메시지 방어]**: 컨슈머가 자기 DB 반영을 끝낸 뒤에야 오프셋을 올리는 **수동 커밋(`Manual Ack`) + 멱등성(`Idempotency`)**, 그리고 영구 실패 메시지(Poison Pill)를 격리해 알람을 받는 **`DLQ(Dead Letter Queue)`** 필수.
