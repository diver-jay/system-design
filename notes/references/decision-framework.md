# 아키텍처 의사결정 프레임워크: 분리(Decoupling) vs 통합(Cohesion) 3대 렌즈

> **핵심 원칙**: *"먼저 단순하게(합쳐서 시작) $\rightarrow$ 수치와 변경 주기로 정당화 $\rightarrow$ 복잡성 추가(분리)"*  
> 시스템 설계와 코드 아키텍처에서 **"왜 A와 B를 분리했는가?"** 혹은 **"왜 합쳐두었는가?"** 라는 모든 질문은 아래 **3가지 축(시간·공간·자원)** 의 양면으로 설명된다.

---

## 1. 한눈에 보는 의사결정 마스터 표 (Decision Matrix)

| 렌즈 (축) | 핵심 키워드 | **분리(Decouple / Isolate)해야 할 때** | **통합(Cohesion / Merge)해야 할 때** | **분리 시 지불하는 세금 (Cost / 부작용)** |
|---|---|---|---|---|
| **① 시간 / 배포축**<br>*(Time & Deploy)* | `Independent Deployability`<br>`Common Closure` | • **변경 이유·주기·팀**이 다를 때<br>• 빠른 배포 주기가 느린 배포 주기에 발목 잡힐 때 | • **항상 같이 수정되고 동시에 배포**되어야 할 때<br>• 단일 팀이 관리하며 배포 조율이 불필요할 때 | • **분산 모놀리식 위험**: 기능 1개 수정에 여러 Repo PR + 배포 순서 조율 지옥<br>• API 버전 하위 호환성 유지 비용 |
| **② 공간 / 스키마축**<br>*(Space & Schema)* | `Design-time Decoupling`<br>`Schema Encapsulation`<br>`DIP` | • 내부 테이블/코드 변경이 **외부(타 서비스·조회 쿼리)로 전파**되는 것을 막을 때<br>• 각자 다른 데이터 모델(3NF vs 검색용 JSON)이 필요할 때 | • **강한 데이터 정합성(`ACID` 트랜잭션)** 과 빈번한 **`JOIN`** 이 필수일 때<br>• 도메인 규칙이 강하게 맞물려 있을 때 | • DB `JOIN` 불가 $\rightarrow$ **`API Composition`**(메모리/네트워크 병목) 또는 **`CQRS`** 강제<br>• 분산 트랜잭션(**`Saga`**, 보상 로직) 및 **`Eventual Consistency`** 복잡도 |
| **③ 자원 / 런타임 / 보안축**<br>*(Resource, Runtime & Security)* | `Fault & Resource Isolation`<br>`Noisy Neighbor 차단`<br>`Least Privilege (최소 권한)`<br>`Blast Radius 축소` | • 한쪽의 무거운 쿼리(`OLAP`), Lock, CPU/메모리 폭주가 **핵심 트랜잭션(`OLTP`)까지 멈추게 할 때**<br>• 트래픽 특성이 달라 **독립 스케일링**이 필요할 때<br>• **보안/권한 격리**: 외부 노출 서버(BFF 등)에 민감한 DB/Vault 접근 권한이나 커넥션을 직접 주지 않고 **공격 표면(Blast Radius)을 통제**할 때 | • **초저지연(`100ns` 메모리 호출)** 이 중요할 때<br>• 리소스 경합이 크지 않고 인프라 비용(유휴 서버/DB)을 아껴야 할 때<br>• 단일 신뢰 경계(Trust Boundary) 내부라 추가 네트워크 홉이 불필요할 때 | • **네트워크 Latency 세금**: 메모리 호출(`100ns`) $\rightarrow$ DC 네트워크(`0.5ms`, **5,000배 지연**) + `N+1` 문제<br>• 중간 프록시/래퍼 서버 추가 시 **홉(Hop) 2배 증가 + SPOF(단일 장애점) 추가**<br>• JSON 직렬화/역직렬화 CPU 소모 및 GC 압박 |

## 2. 잘못 나눴을 때 벌어지는 3대 Hell (실무 페인 포인트 진단)

> *"분리의 이점보다 분리로 인한 세금(부작용)이 더 클 때, 아키텍처는 곧바로 실무의 고통(Pain Point)이 된다."*

### 🔥 ① 시간축을 잘못 나눴을 때: **`분산 모놀리식 (Distributed Monolith)` 지옥**
- **원인**: 실제로는 **변경 주기와 이유가 같아서 항상 같이 수정·배포되어야 하는 도메인**인데, 레포지토리나 서비스를 억지로 쪼개놓음.
- **실무 증상 (Hell)**:
  1. **다중 PR & 배포 순서 조율 지옥**: 기능 하나 수정하려고 2~3개 Repo에 동시에 PR을 올리고, *"A 서버 먼저 배포한 뒤 B 서버 배포해야 안 터집니다"*라며 배포 순서를 수동 조율함.
  2. **배포 파이프라인 병목**: 결국 가장 느린 서비스의 배포 주기에 전체 기능 출시가 발목 잡혀, 모놀리식보다 생산성이 오히려 떨어짐.
  3. **하위 호환성(Backward Compatibility) 강제**: 배포 타이밍이 어긋나 구버전과 신버전이 동시에 떠 있는 시간을 버티기 위해 불필요한 API 버저닝과 방어 코드를 덕지덕지 작성해야 함.

### 🔥 ② 공간축(DB/스키마)을 잘못 나눴을 때: **`JOIN 실종` & `분산 트랜잭션` 지옥**
- **원인**: 빈번하게 함께 조회(`JOIN`)되거나 강한 정합성(`ACID`)으로 묶여야 하는 데이터를 물리적으로 다른 DB/서비스로 쪼개놓음.
- **실무 증상 (Hell)**:
  1. **[조회 지옥] `API Composition`의 양자택일 딜레마** ([`TIL-2026-10-20.md`](../TIL-2026-10-20.md))
     - **인-메모리 조인 선택 시**: 양쪽 서비스에서 대량 데이터를 통째로 긁어와 애플리케이션 메모리에서 합치느라 **Heap 메모리 폭발(`OOM`) 및 `GC 멈춤`** 발생.
     - **ID 기반 순차 조회 선택 시**: A 서비스에서 ID 목록을 뽑아 B 서비스에 건건이(혹은 배치로) 찌르느라 **`N+1` 네트워크 왕복(`0.5ms × N`)으로 응답 속도(Latency) 폭발**.
     - **울며 겨자 먹기 `CQRS`**: 결국 단순 목록 화면 하나 그리려고 Kafka 이벤트 복제 파이프라인과 조회 전용 DB를 따로 구축·관리하는 거대한 배보다 배꼽이 더 큰 비용 발생.
  2. **[쓰기 지옥] `Saga` 보상 트랜잭션 & 정합성 불일치**
     - RDBMS의 공짜 `ROLLBACK`을 못 쓰게 되어, 중간 단계 실패 시 이전 API 호출을 취소하는 **보상 로직(Compensating Transaction)을 개발자가 직접 코드로 구현**해야 하며, `Eventual Consistency` 구간의 CS(데이터 불일치 문의)를 감당해야 함.

#### 💡 쓰기 지옥 해결책 & "HTTP로 묶으면 `ACID`가 될까?" (`HTTP` vs `Kafka`)
- **1순위 해결책 (경계 재조정 — 다시 합치기)**:
  - 항상 동시에 변경되고 즉각적인 `ACID` 정합성이 깨지면 사고가 나는 도메인을 너무 잘게 쪼갠 경우라면, **하나의 서비스/DB(같은 Aggregate)로 다시 합쳐서 로컬 `ACID` 트랜잭션으로 해결**하는 것이 가장 저렴하고 확실한 정답이다.
- **2순위 해결책 (물리적으로 합칠 수 없을 때 — `HTTP`든 `Kafka`든 정합성 세금은 100% 동일)**:
  - **흔한 착각**: *"Kafka(비동기) 대신 HTTP req/resp(동기)로 호출하면 두 DB 사이에 `ACID`가 보장되지 않을까?"* $\rightarrow$ **절대 불가!**
    - `B 서버(결제 DB)`는 `COMMIT` 후 `200 OK`를 보냈는데 **응답길에 네트워크 타임아웃**이 나거나, `A 서버(주문 DB)`가 응답을 받고 **`COMMIT` 직전에 죽으면(OOM/DB 순단)** 돈만 빠져나가고 주문은 롤백되는 **부분 실패(Partial Failure)** 가 터진다.
    - 게다가 DB A의 `@Transactional`을 열어둔 채 느린 HTTP 응답을 기다리면 **DB 커넥션 풀이 순식간에 고갈**된다.
  - **공통 필수 세금 4종**: 따라서 두 DB가 나뉜 순간 **HTTP를 쓰든 Kafka를 쓰든 둘 다 `Eventual Consistency(최종 일관성)`** 이며, 정합성을 맞추려면 똑같이 아래 4가지를 구현해야 한다:
    1. **중간 상태(`PENDING`) 선 커밋**: DB 커넥션을 물고 통신하지 않도록 내 DB에 `PENDING` 상태로 먼저 짧게 `COMMIT`
    2. **멱등성 (`Idempotency-Key`)**: 타임아웃 후 재시도해도 중복 결제/중복 처리가 안 되도록 보장
    3. **보상 로직 (`Saga`)**: 후속 단계 실패 시 앞선 단계를 취소하는 역방향 처리
    4. **중간 유실 복구 메커니즘**: 중간에 서버가 죽어 `PENDING`에 멈춘 데이터를 끝까지 완료/취소시키는 장치

| 비교 기준 | 동기 `HTTP req/resp` (Orchestration) | 비동기 `Kafka 이벤트` (Choreography / Async) |
|---|---|---|
| **정합성 모델** | **`Eventual Consistency`** (절대 `ACID` 아님!) | **`Eventual Consistency`** |
| **유저 UX (응답 타이밍)** | 요청 한 번에 **"결제 완료!" 즉시 응답 가능** (빠른 최종 일관성) | 즉시 완료 응답 불가 ("접수됨" 응답 후 **폴링/웹소켓/SSE 알림** 필요) |
| **상대 서버(B) 장애 시** | B가 죽어 있으면 **A의 API도 즉시 실패** (런타임 강한 결합) | B가 죽어 있어도 **A는 정상 접수**, B가 복구되면 마저 처리 (가용성 격리) |
| **중간 유실 복구 주체 (핵심 차이)** | 개발자가 직접 **`PENDING` 상태 조회 배치(스케줄러/대사 작업)** 를 짜서 주기적으로 재시도·보상 처리를 돌려야 함 | **`Transactional Outbox`** 로 발행만 보장하면, **Kafka 브로커가 디스크에 보관하며 성공할 때까지 재전달**을 대신 해줌 |
| **적합한 비즈니스 특성** | **즉시 거절(Validation/차감)** 이 필요한 핵심 경로 (예: 카드 승인, 좌석/재고 선점, 쿠폰 차감) | 상대가 잠깐 죽어도 **내 요청은 무조건 성공**시키고 나중에 되기만 하면 되는 후속 작업 (예: 카톡 알림, 포인트 적립, 물류 전달, `CQRS` 뷰 동기화) |

- **주의: AWS MSK(Managed Kafka)만 쓰면 자동으로 "무조건 처리"가 보장될까? (No!)**
  - 그냥 `db.save()` 뒤에 `kafka.send()`를 호출하면 여전히 유실된다. 아래 **3대 구멍(발행·보관·소비)** 을 모두 막아야 100% 보장(`At-least-once`)이 완성된다:
    1. **[발행 구멍 — `Dual Write` 방지]**: 내 DB `COMMIT` 직후 `kafka.send()` 전에 서버가 죽어 메시지가 증발하는 것을 막기 위해 **`Transactional Outbox` 패턴**(내 DB 트랜잭션 안에 `outbox` 테이블에도 같이 `INSERT` 후 CDC/Poller로 전송) 필수.
    2. **[브로커 구멍 — 복제 내구성]**: 리더 브로커가 받자마자 죽어도 유실되지 않도록 Producer **`acks=all`** + **`min.insync.replicas`** 설정 필수.
    3. **[소비 구멍 — 유실 및 독성 메시지 방어]**: 컨슈머가 DB 반영을 끝낸 뒤에야 오프셋을 올리는 **수동 커밋(`Manual Ack`) + 멱등성(`Idempotency`)**, 그리고 영구 실패 메시지를 격리해 알람을 받는 **`DLQ(Dead Letter Queue)`** 필수.

### 🔥 ③ 자원/런타임축을 잘못 나눴을 때: **`네트워크 홉(Hop) 낭비` & `SPOF 확산` 지옥**
- **원인**: 물리적 자원 격리(`Noisy Neighbor` 차단)나 보안 경계 목적 없이, 또는 **아무런 비즈니스 부가가치 없는 단순 1:1 패스스루(Pass-through) 래퍼 서버**를 습관적으로 분리함.
- **실무 증상 (Hell)**:
  1. **5,000배 Latency 세금 누적**: 메모리 내 함수 호출(`100ns`)이면 끝날 일이 네트워크 홉(`0.5ms`)과 JSON 직렬화/역직렬화로 바뀌며 응답 시간이 계단식으로 느려짐.
  2. **장애점(`SPOF`)과 인프라 운영비 증가**: 중간에 낀 서버가 죽으면 앞뒤가 멀쩡해도 전체 장애가 나며, 각 구간의 타임아웃(Timeout)·재시도(Retry)·서킷 브레이커를 전부 세팅해야 함.

## 4. 단계별 분리 진화 전략 (클린 아키텍처 Decoupling Modes)

> **"런타임 세금(3번 비용)은 가장 비싸므로 가장 마지막에 지불하라."**

1. **1단계 — 소스 수준 분리 (`Source-Level`)**: 패키지 + 인터페이스(`DIP`)로 **② 공간/스키마 결합**만 먼저 끊는다. (네트워크 비용 0)
2. **2단계 — 배포 단위 분리 (`Deployment-Level`, `.jar`)**: 팀/모듈이 커지면 `.jar`를 나눠 **① 빌드 시간 단축 + 컴파일 타임 강제 차단**을 챙긴다. (네트워크 비용 여전히 0)
3. **3단계 — 서비스 수준 분리 (`Service-Level`, MSA/DB 분리)**: 트래픽 병목(`Noisy Neighbor`)이나 팀 규모 때문에 **③ 물리적 자원 격리**와 **① 완전한 독립 배포**가 불가피할 때만 네트워크/분산 세금을 감수하고 서버와 DB를 쪼갠다.
