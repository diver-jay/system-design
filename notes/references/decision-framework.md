# 아키텍처 의사결정 프레임워크: 분리(Decoupling) vs 통합(Cohesion) 3대 렌즈

> **핵심 원칙**: *"먼저 단순하게(합쳐서 시작) $\rightarrow$ 수치와 변경 주기로 정당화 $\rightarrow$ 복잡성 추가(분리)"*  
> 시스템 설계와 코드 아키텍처에서 **"왜 A와 B를 분리했는가?"** 혹은 **"왜 합쳐두었는가?"** 라는 모든 질문은 아래 **3가지 축(시간·공간·자원)** 의 양면으로 설명된다.

---

## 1. 한눈에 보는 의사결정 마스터 표 (Decision Matrix)

| 렌즈 (축) | 핵심 키워드 | **분리(Decouple / Isolate)해야 할 때** | **통합(Cohesion / Merge)해야 할 때** | **분리 시 지불하는 세금 (Cost / 부작용)** |
|---|---|---|---|---|
| **① 시간 / 배포축**<br>*(Time & Deploy)* | `Independent Deployability`<br>`Common Closure` | • **변경 이유·주기·팀**이 다를 때<br>• 빠른 배포 주기가 느린 배포 주기에 발목 잡힐 때 | • **항상 같이 수정되고 동시에 배포**되어야 할 때<br>• 단일 팀이 관리하며 배포 조율이 불필요할 때 | • **분산 모놀리식 위험**: 기능 1개 수정에 여러 Repo PR + 배포 순서 조율 지옥<br>• API 버전 하위 호환성 유지 비용 |
| **② 공간 / 스키마축**<br>*(Space & Schema)* | `Design-time Decoupling`<br>`Schema Encapsulation`<br>`DIP` | • 내부 테이블/코드 변경이 **외부(타 서비스·조회 쿼리)로 전파**되는 것을 막을 때<br>• 각자 다른 데이터 모델(3NF vs 검색용 JSON)이 필요할 때 | • **강한 데이터 정합성(`ACID` 트랜잭션)** 과 빈번한 **`JOIN`** 이 필수일 때<br>• 도메인 규칙이 강하게 맞물려 있을 때 | • DB `JOIN` 불가 $\rightarrow$ **`API Composition`**(메모리/네트워크 병목) 또는 **`CQRS`** 강제<br>• 분산 트랜잭션(**`Saga`**, 보상 로직) 및 **`Eventual Consistency`** 복잡도 |
| **③ 자원 / 런타임 / 보안축**<br>*(Resource, Runtime & Security)* | `Fault & Resource Isolation`<br>`Noisy Neighbor 차단`<br>`Least Privilege (최소 권한)`<br>`Blast Radius 축소` | • 한쪽의 무거운 쿼리(`OLAP`), Lock, CPU/메모리 폭주가 **핵심 트랜잭션(`OLTP`)까지 멈추게 할 때**<br>• 트래픽 특성이 달라 **독립 스케일링**이 필요할 때<br>• **보안/권한 격리**: 외부 노출 서버(BFF 등)에 민감한 DB/Vault 접근 권한이나 커넥션을 직접 주지 않고 **공격 표면(Blast Radius)을 통제**할 때 | • **초저지연(`100ns` 메모리 호출)** 이 중요할 때<br>• 리소스 경합이 크지 않고 인프라 비용(유휴 서버/DB)을 아껴야 할 때<br>• 단일 신뢰 경계(Trust Boundary) 내부라 추가 네트워크 홉이 불필요할 때 | • **네트워크 Latency 세금**: 메모리 호출(`100ns`) $\rightarrow$ DC 네트워크(`0.5ms`, **5,000배 지연**) + `N+1` 문제<br>• 중간 프록시/래퍼 서버 추가 시 **홉(Hop) 2배 증가 + SPOF(단일 장애점) 추가**<br>• JSON 직렬화/역직렬화 CPU 소모 및 GC 압박 |

## 3. 단계별 분리 진화 전략 (클린 아키텍처 Decoupling Modes)

> **"런타임 세금(3번 비용)은 가장 비싸므로 가장 마지막에 지불하라."**

1. **1단계 — 소스 수준 분리 (`Source-Level`)**: 패키지 + 인터페이스(`DIP`)로 **② 공간/스키마 결합**만 먼저 끊는다. (네트워크 비용 0)
2. **2단계 — 배포 단위 분리 (`Deployment-Level`, `.jar`)**: 팀/모듈이 커지면 `.jar`를 나눠 **① 빌드 시간 단축 + 컴파일 타임 강제 차단**을 챙긴다. (네트워크 비용 여전히 0)
3. **3단계 — 서비스 수준 분리 (`Service-Level`, MSA/DB 분리)**: 트래픽 병목(`Noisy Neighbor`)이나 팀 규모 때문에 **③ 물리적 자원 격리**와 **① 완전한 독립 배포**가 불가피할 때만 네트워크/분산 세금을 감수하고 서버와 DB를 쪼갠다.
